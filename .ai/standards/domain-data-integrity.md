# Domain Data Integrity Standards

Use this file when a project has durable business data, financial records, audit history, billing, payments, external-system synchronization, imports, exports, or any workflow where one record's state must not be confused with another record's state.

These standards apply alongside `database-standards.md` when the data is database-backed and alongside `persistence-and-artifacts.md` when the data is stored in files, reports, logs, JSON, PDFs, exports, or other durable artifacts.

## Purpose

The goal is to make durable business state hard to corrupt and easy to audit.

Review and design should make it clear:

- which durable entity owns each fact or state;
- which references identify exact entities;
- which values are display snapshots rather than references;
- which external identifiers are authoritative only inside an external system;
- how derived views avoid applying one entity's state to another entity;
- how migrations preserve or intentionally reset identity and lineage.

For business-critical data, descriptive similarity is not identity. A student name, date, time, plan title, filename, amount, or status label may help humans understand a row, but it must not be the only link used to apply invoice, payment, completion, audit, tax, import, export, or reconciliation state unless that value is explicitly unique, immutable, and documented as the domain identity.

## Core Principles

- Prefer stable identifiers for durable references.
- Treat names, titles, dates, times, amounts, descriptions, filenames, and formatted text as mutable or non-unique unless the domain explicitly proves otherwise.
- Store both a stable reference and an issued-time snapshot when old output must remain historically accurate.
- Make the authoritative owner of each state transition explicit.
- Do not infer financial, audit, billing, tax, payment, completion, reconciliation, printed, imported, exported, or finalized state from matching descriptive fields.
- Preserve identity through each transformation: UI model, use-case DTO, domain model, persistence entity, artifact writer, report, and read model.
- Make stale or missing references visible and safe. They must not silently attach state to the wrong entity.
- Tests for durable state must include collision scenarios where different entities share the same descriptive values.

## Stable Identity

A stable identity is a value that identifies exactly one durable business object for as long as any data may refer to it.

Good stable identities include:

- database primary keys when they are durable within the same database;
- immutable public IDs generated by the application;
- external-system IDs when the external system owns that entity and the local row records the mapping;
- natural keys only when the business domain guarantees they are unique, immutable, and normalized.

Weak identities include:

- display names and short names;
- addresses, emails, phone numbers, account labels, or customer-entered text;
- dates and times;
- prices, amounts, plan names, invoice titles, or product descriptions;
- filenames or generated report paths;
- compound keys built from mutable or non-unique descriptive fields;
- external IDs reused outside the boundary where they are authoritative.

Natural keys are allowed only when all of these are true:

- the domain says the value is unique and immutable;
- the application validates and enforces that uniqueness;
- persistence has a matching uniqueness constraint where practical;
- the key cannot change because of ordinary user editing, localization, formatting, import cleanup, or external-system refresh;
- collision and rename/edit cases are tested.

If any of those conditions are not true, use a surrogate or generated stable identity and treat the natural value as display data.

## References Versus Snapshots

References and snapshots solve different problems. Do not substitute one for the other.

A reference points to a current durable entity. It is used for ownership, lineage, locking, updates, joins, permission checks, reconciliation, and state application.

A snapshot preserves what was true when an action happened. It is used for invoices, receipts, reports, exports, audit history, legal/tax documents, and old UI display that must not change when current catalog data changes.

Many business workflows need both:

- the reference answers "which exact thing was this about?";
- the snapshot answers "what did the user/customer see or agree to at that time?"

Examples:

- An invoice line should reference the exact local lesson, plan/catalog identity, customer/student, and invoice it belongs to, while also storing issued-time display text and price.
- A payment record should reference the exact invoice or receivable it settles, while preserving payment-time method, amount, date, and external transaction label.
- A report row may display names and formatted dates, but the underlying persisted or reconstructable data should include stable source IDs when later actions depend on it.

## Authoritative State Ownership

For each important state, identify the owning entity and write path.

Ask:

- Which durable row or artifact owns this state?
- Which workflow is allowed to change it?
- Which components may only project or display it?
- Which state is copied for history, and which remains live?
- What happens if the source row is edited, deleted, refreshed from an external system, or recreated?

States that usually require exact ownership include:

- invoiced, issued, finalized, printed, paid, outstanding, credited, refunded, voided;
- completed, cancelled, skipped, rescheduled, deleted;
- imported, exported, reconciled, verified, published, archived;
- tax/VAT applicability and tax registration snapshots;
- plan/catalog identity, price, quantity, period, and commercial terms;
- user/account/customer/student ownership and authorization scope.

Applying any of these states by descriptive matching is a high-risk design. It can be acceptable only when the descriptive key is a documented, enforced stable identity.

## Lineage Through Transformations

Every transformation that carries durable business data should preserve the identifiers needed by later stages.

Review boundaries such as:

- UI display model to command/request model;
- command/request model to domain object;
- draft object to issued/final object;
- domain object to persistence entity;
- persistence entity to query/read model;
- local record to external API payload;
- external API response to local mapping;
- database row to PDF/report/export;
- migration source row to migrated row.

At each boundary, ask:

- Which IDs are required downstream?
- Were any IDs dropped because the display did not need them?
- Can a later component reconstruct identity only by matching descriptive fields?
- Are optional/default IDs allowed to become "unknown but accepted" state?
- Are foreign keys, indexes, uniqueness constraints, and nullability aligned with the domain contract?

If a component drops an ID that a later component needs to apply state safely, that is a data-integrity defect even if the current UI still displays correctly.

## External System Identity

External systems often have their own IDs. Treat them as scoped identities, not universal truth.

For each external ID, document or infer:

- which external system owns it;
- whether it is stable across edits, moves, imports, deletion/recreation, account changes, and calendar/file/folder changes;
- whether the local system owns a row mapped to it;
- whether local audit/billing state can outlive or intentionally diverge from the external object.

When external data is operational scheduling state and local data is billing/audit state, keep those authorities separate. External edits may update local operational rows only while the business state is still editable. Once a local row is billed, issued, paid, exported, reconciled, or otherwise auditable, later external edits must not silently rewrite that local audit state.

## Financial, Billing, Tax, And Audit Data

Financial and audit data require the strongest identity discipline.

For invoices, payments, credits, receipts, tax/VAT calculations, accounting exports, and issued PDFs:

- issued records must be immutable except through explicit corrective workflows;
- line items must reference the exact source entities they bill, credit, or settle;
- displayed names, descriptions, prices, taxes, addresses, account data, and payment terms should be issued-time snapshots when old documents must remain accurate;
- invoice numbers must not be consumed or skipped unless the domain explicitly records the failed/voided number;
- deleting or resetting test data must not be mistaken for a production correction workflow;
- payment state must belong to the exact invoice/receivable, not to rows that merely match amount, date, student/customer, or period;
- tax applicability must be based on the documented business rule and stored inputs, not accidentally on current settings if old invoices are viewed later.

Any review finding where money, tax, invoice, payment, credit, receipt, issued document, or audit state can attach to the wrong durable entity should be treated as Critical unless the impact is clearly bounded to disposable test data.

## Database And Persistence Expectations

When persistence is database-backed:

- use explicit primary keys, foreign keys, unique constraints, and indexes where the database should enforce identity or relationship rules;
- make required references non-nullable once the workflow needs them;
- do not rely on optional/default ID values such as `0`, empty strings, or nulls in finalized records unless they represent a documented legacy or unknown state;
- align EF Core entity fields, domain models, DTOs, migrations, and repository projections so identities are not lost;
- review generated migrations for identity/lineage loss, not only for destructive operations;
- add migration tests when real durable data must be preserved;
- add collision tests for repository queries that apply status or find related records.

When persistence is file/artifact-backed:

- include stable source IDs in durable machine-readable artifacts when future actions depend on them;
- do not use filenames, display headings, or formatted text as the only durable relationship unless they are documented stable IDs;
- preserve enough lineage in reports/logs to diagnose which exact rows were acted on.

## Review Triggers

Apply this standard whenever a change:

- adds, removes, renames, or maps an ID field;
- changes a database schema, migration, DTO, entity, domain model, read model, or report model;
- creates, issues, finalizes, prints, pays, reconciles, imports, exports, deletes, or locks business records;
- groups, deduplicates, matches, joins, or correlates records;
- syncs with an external system;
- displays historical documents or old generated output;
- changes plan/catalog/customer/student/account/payment/tax data used by issued records;
- introduces fallback matching or "best effort" reconciliation;
- changes tests around persistence or durable state.

## Review Checklist

Before accepting a change involving durable business state, ask:

- What is the exact durable entity being changed, billed, paid, displayed, locked, deleted, imported, exported, or reconciled?
- What stable ID identifies it?
- Is that ID carried through every layer and persisted where needed?
- Are display fields treated as snapshots or live references deliberately?
- Can two different entities share the same name/date/time/title/amount/period?
- If yes, are there tests proving state does not cross between them?
- Does the database enforce relationships that the domain depends on?
- Does the application fail safe when a reference is missing, stale, deleted, or ambiguous?
- Are migrations preserving identities or explicitly documenting accepted data reset/breakage?
- Are external IDs scoped to the external system boundary and mapped to local durable IDs when local audit state matters?
- Does generated output preserve historical truth without depending on current mutable catalog/settings data?
- Would this design still be safe after rename, reschedule, duplicate, delete/recreate, import, sync refresh, retry, crash, or migration?

## Severity Guidance

- **Critical**: state involving money, tax, invoice, payment, credit, receipt, audit, finalization, deletion, or data ownership can attach to the wrong durable entity, be silently lost, or be reported falsely.
- **High**: important business state relies on mutable or non-unique descriptive matching, but the known impact is not financial/audit critical.
- **Medium**: identity is preserved today but contracts are loose, tests do not cover collisions, or future changes are likely to break lineage.
- **Low**: naming, documentation, or clarity issue around identity that does not currently threaten correctness.

When uncertain, treat identity ambiguity in durable financial or audit paths as a blocker until proven safe.
